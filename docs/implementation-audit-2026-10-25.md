## 1. 종합 판단

**축제 탐색 화면, 관광정보 API 연동, 대화 조건 추출 및 코스 생성 로직은 구현되어 있다. 그러나 화면에서 실제 AI를 거쳐 코스를 생성·수정하는 통합 흐름은 아직 완성되지 않았다.**

프론트 빌드와 린트는 통과했다. 실제 TourAPI 목록·상세 및 카카오 장소 검색도 응답했다. DB 초기화 후 축제 목록의 날짜·지역·반경 조회도 확인했다. 반면 채팅 API 미등록, 정적 파일 제공 누락, 모의 채팅 유지가 실제 사용을 막는다.

저장소에는 UI 설계서 v0.1의 화면 ID와 설명만 있고 설계서 원본·제출 평가표는 없다. 따라서 전체 요구사항 대비 완성률을 백분율로 산정하지 않았다. 아래의 ‘구현’은 코드 존재와 확인한 범위이며, 모든 화면의 사용자 테스트 완료를 뜻하지 않는다.

## 4. 데이터 및 추천 방식

- 축제 목록: `file/response_searchFestival2_296_261021.json`의 296건을 Chroma에 저장하고 메타데이터 조건으로 조회한다.
- `chroma_insert_data.py`는 고정 스냅샷을 수동 적재한다. 정기 갱신·스케줄러·upsert 흐름은 확인되지 않았다.
- Chroma를 사용하지만 현재 검색은 `.get(where=...)` 중심이다. 의미 기반 벡터 검색이나 RAG 추천으로 설명할 근거는 없다.
- LLM은 대화에서 조건을 추출한다. 실제 장소 선택은 거리, 유형, 일부 취향 분류 및 시간 제한을 적용한 규칙 기반 알고리즘이다.
- 이동 수단은 자동차 기준이다. 도보·대중교통 코스는 구현되어 있지 않다.
- 동행자는 주로 코스 제목에 반영한다. 모든 취향이나 접근성 조건을 만족하도록 최적화하는 기능은 아니다.
- 운영시간은 안내용 표시이며 실제 방문 시각의 영업 여부나 휴무를 검증하여 코스를 배제하지 않는다.

## 5. 제출 전 우선 수정 항목

### P1 — 핵심 동작과 통합

1. **FastAPI 단독 실행 시 화면 자산 404**  
   `main.py:15`에서 `/view` 정적 파일 mount가 주석 처리되어 있다. 빌드 HTML은 `/view/assets/...`를 참조한다. TestClient로 HTML 200, JS·CSS 각각 404를 재현했다. 정적 파일 제공을 복구해야 단일 서버 시연이 가능하다.

2. **채팅 API 404**  
   `main.py:12`는 chat_router를 import만 하고 앱에 등록하지 않는다. `POST /api/chat` → 404를 재현했다. `chat_api.py`에 구현된 라우터를 앱에 등록해야 한다.

3. **화면 채팅은 실제 AI 미사용**  
   `frontend/src/api/chat.js:38,56`의 `USE_MOCK=true`로 mock 응답을 반환한다. 실 API 연결·Ollama 실행 검증 후 전환해야 한다. 현재 화면의 코스 생성 시연은 AI 통합 성공 증거가 아니다.

4. **화면과 채팅 API 요청 계약 불일치**  
   프론트는 region/festival_id/previous_course를 보내지만 `chat_api.py:20-27`은 message/history만 받는다. Pydantic 파싱 결과에서도 추가 필드가 사라짐을 확인했다. 선택 권역, 첨부 축제, 기존 코스 수정 처리를 연결해야 한다. mock 설정만 바꾸면 해결되는 문제가 아니다.

### P2 — 기능 오류와 제출 정확성

5. **행사 조회 보조 API 사용 불가**  
   `main.py:70-73`은 keyword를 필수로 받지만 `tour_api.search_festival`에는 해당 인자가 없다. start_date만 주면 422, keyword를 함께 주면 500을 재현했다. 주 화면에서 쓰는 `/api/festivals`와는 별도 경로이다.

6. **날짜 검증 누락 및 정렬명 매핑 오류**  
   `/api/festivals?startDate=not-a-date` → 500. `chroma.py:58-59,156-158`의 문자열 처리·정수 변환 전에 유효성 검증이 필요하다. `:69-85`에서 distance/startDate/endDate 분기가 `len(arrange)==1` 안에 있어 도달하지 못한다. A/E는 변환되지만 긴 정렬명은 그대로 남는 것을 확인했다. 화면 자체 정렬과 구분해야 한다.

7. **실제 코스의 홈 지도 연결 조건 오류**  
   `frontend/src/pages/HomePage.jsx:77`은 course.region과 권역 코드를 비교한다. 실 백엔드는 지역 이름(예: 강릉)을 반환하므로 변환된 regionCode를 써야 한다. 실제 모드로 전환할 때 드러나는 문제이다.

8. **운영시간·휴무 기능 통합 누락**  
   `course.py:55,223-235,325-336`은 축제 hours와 restDate를 제공하지 않는다. 별도 `feature/place-intro` 작업을 확인해 실제 반환 계약까지 통합해야 한다. 화면 표시 구현만으로 전체 완료라고 쓰면 안 된다.

9. **mock 이동시간 추정 표시 불일치**  
   `frontend/src/api/chat.js:263-266`은 모든 구간을 직선거리로 추정하면서 12km 초과에만 estimated를 붙인다. mock 결과를 실제 길찾기 결과로 오해할 수 있다.

10. **초기화 안내와 실제 코드 불일치**  
    `frontend/README.md:40`은 chroma.py의 insert_data를 안내하지만 실제 진입점은 chroma_insert_data.py이다. `:42`의 채팅 상태 설명도 ‘라우터 파일 존재, 앱 미등록, 화면 mock’으로 갱신해야 한다.

추가 수동 시나리오 확인 대상: 축제를 첨부한 뒤 새로운 지역의 코스를 요청했을 때 이전 festivalRef가 남는 흐름(`CourseProvider.jsx:55-58,80`), mock 수정 후보가 부족한 경우의 null 처리 및 시간 재검사. 이 항목들은 코드상 위험을 확인했지만 브라우저 재현을 완료하지 않았다.

## 7. 제출 문서에 사용할 수 있는 표현

> 지역 축제 탐색과 여행 코스 추천을 지원하는 웹 프로토타입을 개발했다. React 기반 화면에서 축제를 탐색하고 상세 정보를 확인할 수 있으며, FastAPI 백엔드는 TourAPI와 카카오 API, Chroma 기반 축제 데이터 조회를 제공한다. 대화에서 여행 조건을 추출하는 LLM 모듈과 거리·시간 제약을 반영한 코스 생성 로직을 구현했다. 현재 채팅 화면은 모의 응답으로 동작하며 실제 AI API 연결 및 코스 수정 흐름의 통합이 남아 있다.

현재 피해야 할 표현: ‘전체 기능 완성’, ‘실시간 자동 갱신’, ‘벡터 유사도 기반 RAG 추천’, ‘영업시간·휴무를 보장하는 최적 코스’, ‘실제 AI 코스 수정 완료’, ‘서버 일일 사용량 제한 완료’.

## 8. 권장 마무리 순서

1. 정적 파일 mount와 chat_router 등록 복구.

이번 작업에서는 제품 소스를 수정하거나 기능 브랜치를 병합하지 않았다. 최신 코드 수신, 브랜치 전환, 가상환경 의존성 설치, 프론트 빌드, 로컬 DB 초기화 및 이 점검 문서 작성만 수행했다.
